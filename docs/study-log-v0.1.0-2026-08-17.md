## 本阶段目标

本阶段围绕教学文档 1 完成一个最小可运行的 RPC 调用链路。核心目标不是实现完整生产级 RPC，而是先理解并验证：

1. 服务消费者不直接依赖服务实现类，只依赖公共接口。
2. 消费者通过代理对象发起远程调用。
3. RPC 请求能够被序列化并通过 HTTP 发送到服务提供者。
4. 服务提供者能够反序列化请求，根据服务名找到实现类，通过反射执行目标方法。
5. 服务端将执行结果封装成 RPC 响应并返回给消费者。
6. 消费者拿到响应后反序列化，并像调用本地方法一样得到结果。

## 当前模块结构

当前工程按简易 RPC 的角色拆分为几个模块：

- `example-common`：公共接口和模型，例如 `User`、`UserService`。
- `example-provider`：服务提供者，负责注册 `UserServiceImpl` 并启动 HTTP 服务。
- `example-consumer`：服务消费者，负责获取代理对象并调用 `UserService#getUser`。
- `rpc-trial`：RPC 框架核心模块，包含序列化器、请求响应模型、本地注册表、HTTP 服务端、动态代理等能力。

这个结构体现了 RPC 的基本思想：调用方和服务方共享接口定义，但实现类只存在于服务提供者侧。

## 已完成内容

### 1. 公共接口与模型

在 `example-common` 中定义了用户模型和服务接口：

- `User`：用户实体，当前核心字段是 `name`。
- `UserService`：公共服务接口，定义 `User getUser(User user)`。

这一层的作用是让 provider 和 consumer 都能基于同一份接口编程。

### 2. 服务提供者

在 `example-provider` 中完成：

- `UserServiceImpl` 实现 `UserService`。
- `EasyProviderExample` 中通过 `LocalRegistry.register` 注册服务。
- 通过 `VertxHttpServer` 启动 HTTP 服务，监听 `8080` 端口。

当前服务注册方式是本地注册表，服务名使用接口全限定名：

```java
LocalRegistry.register(UserService.class.getName(), UserServiceImpl.class);
```

### 3. RPC 请求与响应模型

在 `rpc-trial` 中定义：

- `RpcRequest`：包含服务名、方法名、参数类型、参数值。
- `RpcResponse`：包含返回数据、返回类型、响应消息和异常信息。

其中 `RpcRequest` 是跨进程调用的关键抽象。一次本地方法调用会被转换为一份可传输的请求对象。

### 4. 序列化能力

当前使用 JDK 原生序列化：

- `Serializer`：序列化器接口。
- `JdkSerializer`：基于 Java 对象流实现序列化和反序列化。

这一阶段重点是跑通链路，因此选择 JDK 序列化足够直观。后续可以对比 JSON、Hessian、Kryo 等方案。

### 5. HTTP 服务端处理器

`HttpServerHandler` 完成服务端核心处理流程：

1. 读取 HTTP 请求体。
2. 反序列化得到 `RpcRequest`。
3. 根据 `serviceName` 从 `LocalRegistry` 获取服务实现类。
4. 根据 `methodName` 和 `parameterTypes` 获取目标方法。
5. 通过反射调用服务实现对象。
6. 将返回值封装为 `RpcResponse`。
7. 序列化响应并写回 HTTP 响应。

这是当前简易 RPC 的服务端主干。

### 6. 动态代理

当前动态代理通过 JDK `Proxy` 实现：

- `ServiceProxy` 实现 `InvocationHandler`。
- `ServiceProxyFactory` 根据接口类型创建代理对象。
- `EasyConsumerExample` 通过 `ServiceProxyFactory.getProxy(UserService.class)` 获取代理。

调用 `userService.getUser(user)` 时，并不是直接执行本地实现类，而是进入代理的 `invoke` 方法，构造 `RpcRequest` 并发起 HTTP 请求。

## 验收结果

本阶段已经完成核心验收。

消费者调试输出：

```text
achingsoul
进程已结束，退出代码为 0
```

该结果说明：

1. 消费者成功创建了 `UserService` 动态代理。
2. 动态代理成功将 `getUser` 调用转换为 RPC 请求。
3. 请求成功发送到 `localhost:8080` 的 provider。
4. provider 成功找到 `UserServiceImpl` 并执行目标方法。
5. provider 成功将返回值序列化后响应给 consumer。
6. consumer 成功反序列化响应并打印返回对象的 `name`。

当前阶段的验收指标：

- provider 启动后能监听 `8080` 端口。
- consumer 调用 `userService.getUser(user)` 后输出 `achingsoul`。
- consumer 退出代码为 `0`。
- provider 控制台能看到收到 HTTP 请求。
- 如果 provider 侧打印用户信息，应能看到服务端也执行了 `UserServiceImpl#getUser`。

## 问题复盘

### 1. `httpServerResponse` 标红

最初 `HttpServerHandler#doResponse` 中变量名不一致，前面定义了响应对象，后面调用时使用了另一个未定义变量名，导致 IDE 标红。

复盘点：

- Java 局部变量名必须一致。
- 跟教程敲代码时，尤其要注意变量名大小写和前后对应关系。
- IDE 标红不一定是依赖问题，很多时候是作用域或变量命名问题。

### 2. `implClass` 为空

调试时曾出现服务端根据 `serviceName` 没有找到实现类的问题。该问题帮助理解了本地注册表的核心作用：

- provider 注册的服务名必须和 consumer 请求中的服务名一致。
- 当前服务名约定是接口全限定名。
- 如果服务名不一致，服务端反射调用前就无法拿到实现类。

### 3. Debug 过程中触发额外调用

调试动态代理时，IDE 展示代理对象可能触发 `toString`、`hashCode` 等方法。这类现象容易干扰理解。

复盘点：

- 动态代理会拦截接口代理对象上的方法调用。
- 调试器为了展示对象，也可能触发某些方法。
- 面试表达时应聚焦业务方法调用链路，不把调试器行为和框架主流程混在一起。

可以这样描述当前阶段项目：

> 我实现了一个简易版 RPC 框架，拆分为服务消费者、服务提供者、公共接口和 RPC 核心模块。消费者侧基于 JDK 动态代理屏蔽远程调用细节，将接口方法调用封装成包含服务名、方法名、参数类型和参数值的 RPC 请求；请求经过 JDK 序列化后通过 HTTP 发送到服务提供者。服务端基于 Vert.x 监听请求，反序列化后从本地注册表查找服务实现类，并通过反射调用目标方法，最后将执行结果封装为响应返回给消费者。目前已经跑通 `UserService#getUser` 的完整调用链路。

这个表达适合简历项目的一阶段描述，重点放在“我理解了 RPC 调用链路”而不是夸大为完整分布式框架。

## 当前能力边界

当前项目仍是教学阶段的简易 RPC，有明显边界：

- 服务地址硬编码为 `http://localhost:8080`。
- 注册中心是本地内存 Map，不支持跨进程服务发现。
- 序列化协议暂时只有 JDK 序列化。
- 网络通信基于 HTTP，暂未自定义协议。
- 没有负载均衡、重试、超时、心跳、服务下线、版本管理等机制。
- 异常处理较基础，暂未区分业务异常、框架异常、网络异常。

这些边界不是缺点，而是后续版本迭代的切入点。
